# 新しいライブAPIを通じてCodexの文字起こし

[English](codex-live-transcription-evaluation.md)

2026年10月21日のアプリケーション評価では、元のオーディオのエクスポート、ローカル分析、一般ノートのインポート、ノートの読み返し、および実際のCodex推論を用いたレンダリング済みオーディオの検査が完了しました。新しいAPIは既存の固定プログラムからの認識結果を保持します。しかし、エージェントが生成した認識器を正確にさせるものではありません。新たに生成されたDSPプログラムは、Basic Pitchよりも大幅に多くの偽ノートを生成しました。

後者の[オーディオのみワークフロー評価](codex-autonomous-cover-evaluation.ja.md)は、凍結されたプログラムを供給せずに修復されたレビュー証拠パスをテストし、セクションに依存した構成も検証します。

[測定記録](../tools/eval/references/codex-live-transcription-2026-10-21.json)は、プログラム、元のドラフト、実際にインポートされたメモ、復元された参照、スコア、会話テキスト、受け入れ時の観察、およびアーティファクト復元制限を保持します。

<a id="what-ran"></a>
## 実行内容

オプトイン`auris-gpui`ウィンドウハーネスは実際のアプリケーションビューとセッションを開き、`agent_attach_files`を通じてWAVを添付し、パネルのコンポーザーを送信しました。`drain_agent`は、ライブ編集、権限チェック、独立した自動レビューを含む実際のワーカーのイベントを処理しました。ワーカーは署名済みのCodex CLI 0.163.0、`gpt-6.1-sol`、高負荷、そして通常の認証済みのライブMCPサーバーを使用しました。モデルのスクリプト上の対照実行はなく、別々の`codex exec`文字起こし実行もありませんでした。

ハーネスは表示、GPU、オーディオデバイスのないテストウィンドウを使用します。これはOSのドラッグアンドドロップ完了や視覚UI検証の主張ではなく、アプリケーション動作テストです。まずネイティブデスクトップ探索を試みましたが、自動化ツールは別々のウィンドウ間でファイルをドラッグできませんでした。レンダリングされたサンプルは数値で確認しましたが、コントローラーもアプリケーションエージェントも試聴したとは報告しませんでした。

各テストウィンドウは、分離されたメモリ内の**AutoReview**ポリシーを使用しました。永続的なユーザー設定は変更されず、保留中のリクエストは手動で承認されず、拒否ルールやバイパスモードも使用されませんでした。通常の編集モードではネイティブコマンドの手動同意が必要になる場合がありますが、これらの結果はデフォルト設定での無人操作を確立するものではありません。

ソースは、以前の監査で使用された同じ[Mutopia SATB *Ode to Joy* score](https://www.ibiblio.org/mutopia/cgibin/piece-info.cgi?id=528)でした：238件の参照イベントが、38.4秒間のピアノおよびリード/弦の録音としてレンダリングされました。ファイル名は匿名でした。参照ノート、MIDI、ベースライン予測、正しさフィードバックはアプリケーションエージェントには提供されませんでした。通常のアプリケーションのテンポ/コードメタデータは引き続き利用可能でした。これは、独立した作品やアコースティック録音ではなく、2つの制御された合成音色による1つの作曲です。

<a id="accuracy-of-the-actual-imported-scores"></a>
## 実際の輸入スコアの精度

マッチングには、50ms以内の正確なMIDIピッチとオンセットが求められ、最大で1対1のマッチングのみが可能です。F1は精度と再現率を兼ね備えています。また、別のメジャーでは、50msまたは参照期間の20%のいずれか大きい方の範囲内のオフセットもチェックします。

| 録音 | 新たに生成されたCodex DSP | 以前の固定Codex DSP | Basic Pitch |
| --- | ---: | ---: | ---: |
| ピアノ、オンセットF1 | 16.00% | 78.12% | 95.97% |
| リード／ストリングス、オンセットF1 | 16.77% | 59.40% | 64.74% |
| ピアノ、オンセット＋オフセットF1 | 13.60% | 70.12% | 92.74% |
| リード／ストリングス、開始 + オフセット F1 | 12.83% | 58.86% | 45.26% |

| 録音/方法 | 推定ノート | 一致 | 追加ノート（FP） | 欠落ノート（FN） |
| --- | ---: | ---: | ---: | ---: |
| ピアノ/新しいCodex | 1,850 | 167 | 1,683 | 71 |
| ピアノ/以前のCodex | 187 | 166 | 21 | 72 |
| ピアノ/Basic Pitch | 258 | 238 | 20 | 0 |
| リード／ストリングス/新しいCodex | 931 | 98 | 833 | 140 |
| リード／ストリングス/以前のCodex | 129 | 109 | 20 | 129 |
| リード／ストリングス/Basic Pitch | 142 | 123 | 19 | 115 |

新しいプログラムの顕著な測定上の失敗は、過剰な検出である。ピアノでは、前プログラムよりも1つの参照イベントだけを一致させながら、1,662件の偽イベントを追加している。これは、解析的ハーモニックプロファイルを補間スペクトルピークに正のフィッティングを用いており、その後に活動セグメンテーションを行う。前プログラムは異なるスペクトル分解と明示的なハーモニック抑制を使用している。これら二つとも、音声を直接認識するモデルではなく、Codexが開発した非訓練済みのDSPである。

前回のプログラムの結果は、混合物におけるより優れたオフセットスコアを含む、以前の実験を再現しています。Basic Pitchはどちらの場合もオンセットF1を依然として優位に捉えますが、混合物における238件の参照イベントのうち115件を捉えきれません。これらのデータは、認識品質評価をAPIの正常な配信とは別に実施することを支持しますが、Basic Pitchをランダムに生成された分析コードに置き換えることを支持するものではありません。

<a id="acceptance-and-assistance"></a>
## 受諾と支援

4つのCodex実行すべては、`export_audio_attachment`と`import_transcription`を使用し、`create_piano_cover`は使用していませんでした。元のバイトハッシュと実際のプログラムハッシュは、保存されたドラフトに対して独立して確認されました。実際のドキュメントのメモは採点されました。既存のトラックとテンポは保持され、変更はホスト承認前に保存されず、1つのUndoは元のプロジェクトを復元し、Redoはインポートされたプロジェクトを復元しました。その後、ホストのみが結果を配信用に保存しました。

新しいプログラムのSHA-256は`8f5478708e0538737a5b8d1d8965cd5a6b8b7efc1d79307017d40c4de67fa1ba`です。古いプログラムは`1ad425dd3758b046d23c3e3a11bee0ce2815402fda64fc69f77a9cdd873c08b5`のままです。古いプログラムの変更されていないイベントは、スキーマアダプターを通じて明示的に公開された均一強度0.65を受け取ります。新しいプログラムは相対的な適合振幅を推定しますが、どちらも元のMIDIダイナミクスを復元しません。

ホストは、ネイティブコマンドのレビューのため一時停止された後、新しいプログラムの最終的な提案された追加を機械的に組み立てた。認識ロジックやスコアを使用した再チューニングは変更されなかった。後日、レビュー証拠として完全なソースが提供された。したがって、4回の完了した実行は、不十分なWAVリクエストからの無人完了ではなく、**アシスタント付きの固定方法適用ワークフロー**を示している。84〜111秒の実行時間は、以前のコード開発や失敗した試行を除外している。4つの凍結された出力は、実行後、プログラムの編集や追加の推論なしに、エージェントの外で正確に再現された。

<a id="workflow-problems-found"></a>
## ワークフローの問題が見つかりました

1. **大規模なネイティブコマンドは自動レビューの容量を超えています。**最初の試行
シリアライズされたレビューリクエストが64 KiBを超えたため、222.52秒後に停止しました。ネイティブアイテムだけで約23.7 KiBを消費しており、繰り返されるコマンド表現やJSONエスケープもレビュー予算を消費しています。その試みではプログラムやメモはインポートされていませんでした。より小さく意味のあるコード記述ステップはレビューに合格しました。
2. **レビューアはスクリプトや以前の呼び出しの証拠が不足しています。** スプリットコードの試みが停止しました。
実行前に既存のスクリプトを検査できなかったため、383.85秒後に停止しました。フルソースを供給すると、このケースが解決しました。別の実行では、別々に完了したハッシュ検証が次のレビューに利用できなかったため、58.73秒後に停止しました。同じ実行コマンドにfail-closedハッシュチェックを追加すると、このケースが解決しました。承認証拠は、参照ファイルの内容と関連する検証結果を制限された方法で保持する必要があり、権限を上げるか、失敗したレビューを自動的に受け入れることは解決策ではありません。
3. **エージェントは、インポート前にプレビューすることがあります。** `inspect_audio`と呼ばれる2回の試行があります。
空の設定で実行したところ、正しい範囲エラーが発生しました。完了したすべての実行で、インポート後に検査に成功しました。ツール注文のガイダンスはまだ改善が必要です。
4. **手法生成は不安定です。** 前のプログラムと新しいプログラムは非常に
同一の録音に対して異なる精度がある。比較前にコードと閾値は凍結されなければならず、認識エラーはAPIの成功と別に報告される。

完了した4つの試行に加えて、3つのブロックされた試行は観察として保留されています。ソース/ハッシュ証拠も再試行も、音楽の正しさに関するフィードバックを提供したり、凍結された認識器を変更したりしていません。

<a id="artifact-recovery-and-reproduction"></a>
## アセットの復元と再現

パッケージング中に、一時的な`target/`ディレクトリが消えてしまいました。生成されたプロジェクト、プログラム、ノートJSON、ソースWAV、保存された会話はそれぞれ別の評価ワークスペースに残り、Gitでは無視され通常の`cargo clean`では生存する`.local-evaluations/codex-live-transcription-2026-10-21/`にコピーされました。生の揮発性ツールトレースと初期ログファイルは失われました。この記録は以前観察されたハーネスのアサーションと生存するアーティファクトを区別しますが、虚構のMCPまたは承認イベントを再構築することはありません。

独立した参照は公開MIDIから再生成されました。古いアノテーションJSONの正確なバイト列は保証されていません。復元された参照イベントは、3つの歴史的な固定Codexのマッチング指標と、最初に観測されたすべての新しいプログラムカウントをすべて再現します。実際にインポートされたプロジェクトと元のドラフトハッシュは引き続き利用可能です。Basic Pitchの推論と配信エクスポートは、保護された場所に再構築されました。

そのローカルの`delivery/`フォルダには、`fresh-piano`、`fresh-mixture`、`previous-piano`、`previous-mixture`、`basic-piano`、`basic-mixture`に対応した`Cover.auris`、`cover.wav`、`inspection.txt`が含まれています。6つのPCM24ステレオ48 kHzエクスポートすべてが、フルスケールサンプルが0である状態でエンコードファイルチェックに合格しました。測定記録にはそれらのハッシュ値が保持されています。Basic Pitchの推論専用の実行時間は、またエクスポート、コマンドのレビュー、結果のインポートおよび検査も行うエージェントのターンと比較することはできません。

新しいアプリケーションを実行するには、絶対パス `workspace`、`output`、`audio`、`prompt`、`model`、`effort`、`timeout_seconds` を使用した新しい評価構成を作成してください。`target/` 以外の出力パスを使用してください。numpy、scipy、soundfile、matplotlib を使用した uv 環境を準備してください。プロンプトにそのインタプリタを明示的に指定してください。このテストは、サインイン済みの Codex 使用と独立したレビュー使用を消費します。

```powershell
$env:AURIS_CODEX_TRANSCRIPTION_EVAL = 'C:/absolute/evaluation/config.json'
cargo test -p auris-gpui --bins -- --ignored --exact ui::agent_chat::transcription_eval::installed_codex_transcribes_via_new_apis_in_the_window --nocapture --test-threads=1
```

完全なオリジナルハーネスレポートを使用して、厳格なツール結果とアーティファクトチェックを使用して、対応するBasic Pitchベースラインに対してスコアを付けます。

```sh
uv run --with numpy --with scipy tools/eval/live_transcription.py manifest.json basic-pitch-score.json --case ode-piano=/absolute/piano/result.json --case ode-mixture=/absolute/mixture/result.json --json comparison.json
uv run --with numpy --with scipy --with pytest pytest tools/eval/test_live_transcription.py tools/eval/test_piano_transcription.py
uv run --with ruff ruff check tools/eval/live_transcription.py tools/eval/test_live_transcription.py
```

通常のワークスペーステストは、19件のオプトイン/リソーススキップを伴い4,272件に合格しました。Clippyは合格しました。Python測定テストは、変更されたオーディオ、プログラム、注釈、メモ数、既存の音楽、Undoの証拠を含む17件に合格しました。これらの結果は、両手での再生可能性や主観的なカバー品質を確立するものではありません。
