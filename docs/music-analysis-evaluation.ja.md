# CPU 転写: 時系列デコードと評価

[English](music-analysis-evaluation.md)

2 回目の CPU 実装では、ビブラートによる音符の断片化を減らしました。既存のデスクトップ、CLI、モデルツールのコマンドから利用でき、新しいセットアップや重みは必要ありません。音声レポートのアルゴリズム識別子は `cpu-spectral-yin-v2` です。

<a id="what-changed"></a>
## 変更点

最初の実装では、各フレームで1つの周期を選び、独立に丸めていました。ビブラートが半音の中間点を越えると、1つの発音中の音が多数の短い音符に分割されることがありました。新しい実装では、連続した周期候補を最大6個保持し、それらを近い音符の識別子へ射影して、時間方向に低コストな系列を求めます。不要な変化にはペナルティを与えますが、本当の持続的な半音ステップは許容します。無音にも独自の状態があります。差分関数の窓はタイムスタンプを中心に取り、フレーム前半を測定することで生じる系統的な遅延を避けます。

候補生成とデコーダーの分離は、[Mauch と Dixon の pYIN 論文](https://webspace.eecs.qmul.ac.uk/s.e.dixon/pub/2014/MauchDixon-PYIN-ICASSP2014.pdf)を参考にしています。この実装は手作業で設定したコストとコンパクトな音符状態探索を使い、論文のしきい値分布や確率モデルは使いません。pYIN の再現でも学習済み予測器でもありません。各フレームで保持するのは有声音状態最大8個と無音状態1個です。共有される最小コストを引くことで、長いファイルでの浮動小数点誤差の蓄積を避けます。キャンセルは前向きデコードとバックトラッキングの両方で確認します。

<a id="identical-inputs-show-less-fragmentation"></a>
## 同一入力で断片化が減る

診断ジェネレーターはリポジトリ内のオリジナルコードです。11,025 Hz、4.5 秒、モノラル PCM のフィクスチャを9個生成します。各調性フィクスチャには基準音符が8個あり、2つのネガティブコントロールには音符がありません。9個すべての PCM の SHA-256 ハッシュは、保存済みの [v1 結果](benchmarks/transcription-v1.json) と [v2 結果](benchmarks/transcription-v2.json) の間で一致します。v1 のベースラインにはコミット `895bf15` のバックエンドを使い、取得時には評価ツールだけを追加しました。その後、同じフィクスチャジェネレーターを変更後のバックエンドで実行しました。

| 診断 | v1 推定音符数 | v2 推定音符数 | v1 onset F1 | v2 onset F1 | v1 onset+offset F1 | v2 onset+offset F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| クリーンなサイン波 | 8 | 8 | 1.000 | 1.000 | 1.000 | 1.000 |
| ビブラート、±65 セント、5.5 Hz | 29 | 8 | 0.216 | 1.000 | 0.000 | 1.000 |
| 基音が弱く第2・第3倍音が強い | 8 | 8 | 1.000 | 1.000 | 1.000 | 1.000 |
| レガートの半音ステップ | 8 | 8 | 1.000 | 1.000 | 1.000 | 1.000 |
| 同じ音高の反復音符 | 8 | 8 | 1.000 | 1.000 | 1.000 | 1.000 |
| 4段階の音符レベル | 8 | 8 | 1.000 | 1.000 | 1.000 | 1.000 |
| 20 ms の内部ドロップアウト | 10 | 10 | 0.889 | 0.889 | 0.667 | 0.667 |
| 決定論的ノイズ | 0 | 0 | — | — | — | — |
| DC 信号 | 0 | 0 | — | — | — | — |

指標には最大一対一二部マッチングを使うため、重複した予測が同じ基準音符をそれぞれ取り合うことはありません。音高の許容誤差は50セント、オンセットは50 ms、オフセットは基準音符の長さの20%と50 msの大きい方です。これらの基準は [mir_eval の転写メトリクス](https://mir-eval.readthedocs.io/latest/api/transcription.html)に従います。オンセットのみのスコアもオンセットとオフセットのスコアも、音高の一致を必要とします。空のケースは JSON では F1=0 と報告されます。上のダッシュのような場合は、偽陽性の数を確認してください。

これらはエンジニアリング用の診断であり、保留データや実録音の精度推定ではありません。開発中にケースが見えており、マイク、部屋の残響、実際の楽器のさまざまなアーティキュレーションを表すには単純すぎます。ドロップアウトの結果が変わらないのは固有の制限です。短い中断は、同じ音高の本当の再アタックに似ることがあります。別の音への滑らかなビブラートでは、推定境界が数フレーム動くこともあります。これまでどおり、ドラフトを確認して修正してください。

<a id="cpu-cost-stays-small-on-the-development-machine"></a>
## 開発マシンでの CPU コストは小さい

2026-09-07、Windows x86_64、AMD Ryzen 7 9800X3D、リリースビルド、逐次解析ワーカー1つという条件で、3分のステレオパルスフィクスチャは BPM／コードに0.218秒、転写を含む全体に0.416秒かかりました（リアルタイム係数はそれぞれ0.0012と0.0023）。推定された先頭テンポは120.127 BPMで、ドラフトには想定どおり A4 の音符が360個ありました。コンパイル中の別の実行では0.282秒と0.433秒となり、通常のタイミング変動があることを示しています。

スタンドアロンの計測プロセスでは、Windows の `PeakWorkingSet64` を10 ms間隔でポーリングし、ピークワーキングセット21.56 MiBを記録しました。これはフィクスチャの構築と2つの解析パスを含み、増分割り当ての前後を測ったものではありません。DAW、ファイルデコード、ソースのリサンプリングは含まないため、高サンプルレートのインポートファイルに対するメモリ上限ではありません。このワークロードから外部計算資源を要求する理由はありません。

<a id="reproduce-or-evaluate-a-recording"></a>
## 録音を再現または評価する

```sh
cargo test -p auris-analysis --all-targets
cargo run -p auris-analysis --release --example evaluate_transcription > diagnostics.json
cargo run -p auris-analysis --release --example measure_analysis

auris transcribe-audio isolated-melody.wav > estimate.json
cargo run -p auris-analysis --release --example evaluate_transcription -- reference.json estimate.json
```

2ファイルモードでは、各 JSON ファイルの `notes` フィールドだけを読み取ります。MIDI の音高番号（小数の半音も可）と、音声ファイルの先頭からの、伸縮していない秒数を使います。

```json
{"notes":[{"pitch":69,"start":0.2,"end":0.8}]}
```

基準ファイルと推定ファイルのハッシュに加え、precision／recall／F1 と偽陽性／偽陰性の数を別々に出力します。無効な音高・タイムスタンプや、比較サイズが大きすぎる場合は拒否されます。比較は1ファイルあたり最大10,000音符、候補ペア400万件に制限されます。これを超える素材には抜粋を使ってください。元の CLI レポートには追加フィールドがありますが、このメトリクスリーダーでは無視されます。

録音ベンチマークでは、音声ハッシュ、録音者／演奏者の識別情報、権利、抜粋の境界、独立してレビューしたアノテーションを、これらのレポートと一緒に保持してください。開発用録音と評価用録音は分けます。研究計画にある30〜50抜粋のパイロットは、実録音の精度を主張する前に引き続き必要です。コミット済みのジェネレーターと JSON レポートにより、データセットやモデルをダウンロードしなくても、現在の合成データに関する主張を検証できます。
