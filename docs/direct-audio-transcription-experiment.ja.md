# 直接音声LLM文字起こし実験

[English](direct-audio-transcription-experiment.md)

2026年10月21日のローカル実験では、テストされたGemma 4/Ollama接続からの直接ノート予測でBasic Pitchを置き換えることはサポートされていませんでした。1つの構成では無音時にノートを生成し、もう1つの構成では空のドラフトを返却しました。これらは、すべてのオーディオモデルや、個別の分析ツールを選択・使用できるエージェントに関する結論ではなく、2つの特定のローカル構成における結果です。

[測定記録](../tools/eval/references/direct-audio-transcription-2026-10-21.json)は、固定プロンプト、モデルアーティファクトのダイジェスト、実行環境バージョン、元のモデル応答、トークンの使用量、経過時間、入力/参照ハッシュ、および各ケースの指標を保持します。この実験の一環として、プロダクション文字起こしの動作は変更されません。

<a id="input-and-isolation"></a>
## 入力と隔離

入力は、[ピアノ転写評価](../tools/eval/references/piano-transcription-2026-10-21.json)からの12曲のホールドアウトされた作曲者の録音と同一です：シティポップ、ジャズトリオ、オーケストラ、seeds 901/902。それぞれピアノとネイティブミックスとしてレンダリングされています。凍結された楽譜には、同時ユニゾンの融合後に924の参照イベントが含まれています。これらは独立したアコースティック演奏ではなく、制御された合成録音です。

各モデルは、元のWAVバイトを含む新しいシングルユーザーメッセージと、MIDIピッチおよび開始/終了秒の固定リクエストを受け取ります。スコア、ファイル名、プリセット名、BPM、コード推定値、またはBasic Pitch候補は送信されません。推論はアノテーションを開かず、別のスコアリングコマンドで後から開きます。モデルにはトランスクリプションツールは利用できません。これにより認識コンポーネントが分離され、Aurisのツール選択、ライブ編集、または反復的なアレンジエージェントは実行されません。

ローカルにインストールされているモデルである`gemma4:e2b`と`gemma4:e4b`の両方でオーディオサポートが提供されています。サーバーはOllama 0.40.5です。リクエストには`/v1/chat/completions`、`input_audio`、温度0、`reasoning_effort: none`、JSONオブジェクト出力、および8,192トークンの予算が使用されます。[pinned server adapter](https://github.com/ollama/ollama/blob/v0.40.5/openai/openai.go)は`input_audio`を解読し、ここで使用されている出力/推論フィールドもサポートしています。オーディオはlocalhostで引き続き使用され、新しいウェイトや有料API推論は使用されません。

<a id="same-recording-comparison"></a>
## 同じ録音比較

マッチングは、既存のスコアラーと同様に、正確なMIDIピッチと50msのオンセット許容度を使用し、最大1対1のマッチングを行います。F1は適合率と再現率を組み合わせた指標であり、主観的な音楽品質スコアではありません。ベースラインの推定値と録音のハッシュは、以前に公開されたBasic Pitch測定値と比較されました。

| 認識器 | マッチングされた | 追加候補者（FP） | 欠落（FN） | オンセットF1 | 観測された秒数/ファイル |
| --- | ---: | ---: | ---: | ---: | ---: |
| 現在のBasic Pitch | 637 | 327 | 287 | 67.48% | 0.27 |
| Gemma 4 e2b、直接 | 2 | 183 | 922 | 0.36% | 5.48 |
| Gemma 4 e4b、直接 | 0 | 0 | 924 | 0.00% | 2.56 |

直接行は、ソースの長さを超えても続く候補を含む、完全にパース可能な生の候補をスコア付けします。それらは黙って切り落とされたり修復されたりしません。4つのe2bドラフトは長さチェックに失敗します。無効なドラフト全体を拒否すると、1つのマッチが残ります（67 FP、923 FN、F1 0.20%）。12件のe4b結果すべては、音声が添付されていないとする構造的に有効な空の配列です。空の配列は成功した認識ではありません。

Basic Pitchの時間は、同じ録音に対する過去のRust測定値です。直接測定時間は、ローカルのHTTP、オーディオ処理、生成を含むものです。これらはインターリーブした速度ベンチマークではなく、観測されたコストです。ローカル実行には有料の推論呼び出しは発生せず、クラウド料金や電力コストを推定するものではありません。

<a id="controls-and-failure-investigation"></a>
## 制御と故障調査

3つの6秒間のコントロールには、無音、6つの独立したサイン波ノート、そして2つの3音のコードが含まれています。その正確な注釈とオーディオハッシュは記録に保持されています。スコアリングプロンプトには例示ピッチは提供されていません。

* 音声優先の主条件では、e2bは同じC4ノートを10個繰り返して返しました。
3つの制御すべてで10秒まで延長されます。3つすべてが期間チェックに失敗し、生の候補の一致数は0です。e4bは3つすべてに対して空の配列を返しました。
* 部分の順序だけを指示優先に変更し、Aurisのネイティブな添付ファイル順序に合わせても、制御は復元できませんでした。e2bは無音に6つのノートを発明し、e4bも無音にノートを発明しました。両方の構成で、音高のある制御の一致数は0です。1つのe2b応答はトークン予算を使い切り、不完全として拒否されました。
* 主要な音声優先条件からJSON出力制約だけを取り除くと、拒否／音声なしの主張またはコードフェンス内のJSONになり、正確なノートとして扱われません。生の応答は保持されますが、文章やフェンス付きJSONは完了したノートの草案として解釈されません。
* 別の音声によるポジティブコントロールでは、オフラインで合成された文の単語が求められます。
E2bはどちらの部分順序でも文を正しく生成します。e4bは空の回答または繰り返される音節を出します。したがって、宣伝されている機能と成功したHTTP呼び出しにもかかわらず、信頼できる意味音声認識のために入力接続は検証されていません。
* オーディオが完全に省略された場合でも、e2bはJSONリクエストの下で依然としてノートシーケンスを生成します。
e4bでは音声がないと報告します。構造化された出力だけでは、認識の証拠としては不十分です。
* ネイティブの`/api/chat`診断は、互換性アダプターを使わず、指示とWAVバイトを1つのメッセージにまとめます。
2,048トークンの制限でも、e2bは6音のコントロールに対して繰り返されるC4ノートを生成します。e4bは切り詰められた音階のようなシーケンスを生成し、音声リクエストはHTTP 500で失敗します。これらは別の一致コホートによる精度比較ではなく、追加のルーティング検査です。

初期のA4転送プローブは刺激に一致する例示ノートを返しました。この結果はすべての音楽スコアリングから除外されます。診断応答時間はワークスペースのコンパイルと重なり、主要なタイミング比較には含まれませんでした。ホールドアウト録音にはスコア駆動によるプロンプトチューニングはありませんでした。代替の入力順序／出力形式の試行では、制御のみが使用されました。

この実験では、モデルトレーニング、量子化、プロンプト、ローカルのオーディオ・ランタイムの制限を、すべての失敗の原因として単独で分離することはできません。特に、e4bの音声制御の失敗により、空の音楽結果を音楽能力にのみ帰するのは不可能です。HTTPの成功、非ゼロのオーディオトークン、そして聴取に関する流暢な主張は、正しい解釈を確立するものではありません。

<a id="reproduce"></a>
## 再現する

既存のスコアラーと同様に、numpy/scipy、pytest、ruff を使用した `uv` 環境を使用してください。すでにインストール済みのオーディオ対応モデルを使用して、設定済みのローカルサーバーを起動します。既存の例を使用して固定コーパスを生成し、その manifest/audio は変更しないでください。以下のすべての出力ディレクトリとレポートはすべて新規でなければなりません。

```sh
uv run --with numpy --with scipy tools/eval/direct_audio_transcription.py controls target/direct-controls
uv run --with numpy --with scipy tools/eval/direct_audio_transcription.py infer target/direct-controls/manifest.json target/direct-e2b-controls --model gemma4:e2b --split control
uv run --with numpy --with scipy tools/eval/direct_audio_transcription.py infer target/piano-transcription/corpus-v1/manifest.json target/direct-e2b-heldout --model gemma4:e2b
uv run --with numpy --with scipy tools/eval/direct_audio_transcription.py score target/piano-transcription/corpus-v1/manifest.json target/direct-e2b-heldout target/direct-e2b-score.json --baseline target/piano-transcription/candidate-confirmed
```

`--model gemma4:e4b`と新しい出力パスで繰り返してください。制御のみの診断を行う場合は、`--text-first`または`--unconstrained`を別々に使用してください。テストは、アノテーションの分離、無効なピッチ/タイムの拒否、完全なJSON要件、および別々の生の/受け入れられた指標の検証を行います：

```sh
uv run --with numpy --with scipy --with pytest pytest tools/eval/test_direct_audio_transcription.py tools/eval/test_piano_transcription.py
uv run --with ruff ruff check tools/eval/direct_audio_transcription.py tools/eval/test_direct_audio_transcription.py
```

次に有用な実験は、コントローラーが分析ツールを選び、その証拠を演奏可能なアレンジメントに変換することであり、認識、アレンジ、反復修正は別々に評価することです。現在の結果は、認識器を取り除き、これらのローカル接続から未検証のノートJSONを信頼することを支持する証拠を提供していません。
