# 音声だけで行う Codex カバーとセクション対応作曲

[English](codex-autonomous-cover-evaluation.md)

2026-10-21 の追跡評価では、解析コード、インタープリターのパス、参照音符、手動承認を渡さず、添付 WAV と短いリクエストから編集可能なカバーを完成させました。通常のリクエストでは付属の Basic Pitch を選び、独立リクエストでは独自の DSP を生成・実行してから `export_audio_attachment` と `import_transcription` を使いました。

[測定記録](../tools/eval/references/codex-autonomous-cover-2026-10-21.json)には、プロンプト、観測したツール／レビュー結果、実際にインポートした音符、固定したプログラム、ハッシュ、パッケージ、出力を保持しています。完全なツールトレースとプロジェクトスナップショットは `.local-evaluations/codex-autonomous-2026-10-21/` に残っています。

<a id="review-fixes-and-the-initial-blocked-trial"></a>
## レビュー修正と最初のブロックされた試行

以前の [支援付き評価](codex-live-transcription-evaluation.ja.md)では、レビュー入力予算を超える重複したコマンド表現と、スクリプト／以前の呼び出しの証拠不足が見つかりました。新しい [レビュー証拠経路](agent-review-evidence.ja.md) は、損失のない共有テキスト、範囲を制限した現在のスクリプトスナップショット、最近完了したネイティブ結果を使います。操作テキストは保持し、承認レビュー後に現在のパス／ハッシュを再確認します。通常の権限ルールが引き続き優先されます。長い入力の回帰テストは、以前失敗したサイズパターンをそのまま検査し、実際の独立実行は、ソースをユーザーリクエストに貼り付けずにスクリプトの作成、実行、連続した改善を行います。

最初の独立試行は39.17秒後に停止しました。レビュー担当者は、Python を探す際にホームディレクトリ（隠しフォルダーを含む）を不要に列挙したことについて質問しました。そのコマンドは実行されていません。現在のネイティブガイダンスでは、ランタイムの検出を専用の実行ファイル／uv クエリとプロジェクト内環境に向けています。同じユーザープロンプトでの新しい再試行は完了しました。ブロックされた試行は保持しています。これは、すべてのレビューが無人で承認される、または承認されるべきだという主張ではありません。拒否を上書きせず、永続的なルールも変更していません。

<a id="conditions"></a>
## 条件

これは実際のアプリケーションワーカーのテストです。GPUI ウィンドウハーネスがパネルを送信し、実際のワーカーイベントを排出し、認証済み MCP サーバーを通じてライブのセッション操作を実行します。Codex CLI 0.163.0 は `gpt-6.1-sol`、高い effort、分離したインメモリ AutoReview 設定で使いました。ハーネスにはディスプレイ、GPU、オーディオデバイスがなく、OS のドラッグ＆ドロップやデスクトップの視覚検証は確立しません。

各ケースは、リポジトリ外の別プロジェクトで、以前の会話や分析ファイルなしに開始しました。コントローラーが渡したのは WAV と短いリクエストだけです。独立エージェントは uv を通じて Python を検出し、自分のプロジェクト環境に numpy/scipy/soundfile をインストールしました。正確性のフィードバックなしに、ソース波形を使って分析を検査・改善しました。採点は、最終コードとドラフトを保存して完了した後だけ始めました。

録音は、以前の評価で使った公開 Mutopia SATB *Ode to Joy* スコアによる、38.4秒の合成ピアノ演奏と同じで、参照イベントは238個です。バイトハッシュは `049e881f2939744ad9643c69d1d20cdb790b95654ac716080678d820b2e81410` です。MIDI、参照、タイトル、以前の推定値は伏せました。通常のプロジェクトメタデータは利用できました。これは管理された録音1件であり、実録音のコホートでも、楽器をまたいだ安定した認識の実演でもありません。

<a id="cover-results"></a>
## カバーの結果

| リクエスト | エンドツーエンド時間 | インポート音符 | 一致 | 余分 | 欠落 | Onset F1 | Onset + offset F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 通常、エージェントが Basic Pitch を選択 | 36.07 s | 258 | 238 | 20 | 0 | 95.97% | 92.74% |
| 独立 DSP、ランタイムガイダンス後 | 384.64 s | 222 | 217 | 5 | 21 | 94.35% | 76.09% |

マッチングは正確な音高、最大一対一マッチング、50 msのオンセット許容誤差を使い、オフセットには max(50 ms, 参照時間の20%) を許容します。スコアラーは、エージェントの完了文や丸めたツール表示ではなく、実際のプロジェクトテンポを通じて保存された音符ティックを読みます。両方の完了実行は、インポート後に音符を読み戻し、レンダーした音声を検査しました。通常の結果は、3つすべての一致指標で固定した Basic Pitch ベースラインを再現します。

独立プログラムは、複数エンベロープの調波スペクトルフィット、非負フィット、波形オンセット整列、高オクターブ除外を使います。学習済み転写モデルも Basic Pitch も使いません。出所ハッシュは `29dbab4f7857dbe436f5c7d0315e6fac5e9480fe3495e23c0fb6892f9e7b9aaa` で、元の `transcribe.py` のバイト列に続けて `refine.py` のバイト列を連結した SHA256 として検証済みです。個別ファイルとハッシュはすべて保持しています。元の MIDI ベロシティではなく相対的なスペクトル強度を復元し、不確かな弱い音符、オクターブ、リリース、欠落したペダル復元を明示します。

これは推論、レビュー、環境セットアップ、分析、読み戻しを含むエンドツーエンドの観測で、CPU ランタイムのベンチマークではありません。以前に新しく生成したプログラムより独立方式のスコアが大幅に良かったとしても、安定した方式生成は示しません。リクエスト、支援、生成コードが異なるためです。

両ワークフローで、ミックス調整を含む複数の Undo 可能な編集を行いました。そのため、完了したワークフロー全体を1回 Undo しても初期ドキュメントには戻りません。Redo は完全な最終状態を復元しました。各音符インポートの単一トランザクション保証は、セッションテストで引き続き対象です。ハーネスが最終ドキュメントを承認して保存するまで、ライブ作業は未保存でした。下記の WAV 出力はその後コントローラーが作成したもので、ライブエージェントは保存済み WAV の配信や主観的な聴取を主張していません。

<a id="new-composition-includes-structure"></a>
## 新しい作曲には構造が含まれる

リクエストは、メロディーと伴奏を含む明るい16小節のポップ曲を作るだけでした。セクション名は指定していません。58.21秒で、エージェントは4トラック、540音符、128 BPM と、次の実ドキュメントのセクション位置を生成しました。

| セクション | 小節 |
| --- | --- |
| Aメロ | 1–8 |
| サビ | 9–14 |
| エンディング | 15–16 |

すべてのクリップは17小節目の排他的な開始位置で終わり、セクションレーンはそこで名前なしになります。これらのラベルは保存済みプロジェクトにも残ります。作曲ガイダンスは現在、キー／コードメタデータに加えて適切な名前付き形式を要求します。ライブの `edit_harmony` は `section` 単独またはハーモニーとの組み合わせを受け付け、範囲を制限した編集で音符を保持し、範囲内のセクション変更を置き換え、範囲後に以前のラベルを復元して一緒に Undo します。イントロ／ブリッジのセクションは音楽上の選択であり、短い曲のすべてに必須のラベルではありません。既存の song-spec 作曲はすでに形式を保存しています。

<a id="remaining-tasks-and-local-outputs"></a>
## 残る課題とローカル出力

この評価時点では、前後のパディングと BPM／拍推定が未解決でした。両方のカバーはプロジェクトのデフォルト120 BPMを保持しましたが、ソーススコアは100 BPMです。ソース秒のタイミングは保持されますが、音楽を小節グリッドに合わせたり、ソーステンポを推定したりはしません。パディング除去では、ピックアップ、静かなアタック、リリース、結果として生じるソースからスコアへのオフセットを考慮する必要があります。これらの課題は、より良い承認証拠やインポートの成功だけでは修正されません。

ローカルの `delivery/ordinary`、`delivery/independent-2`、`delivery/composition` フォルダーには、それぞれ `Cover.auris`、`cover.wav`、`inspection.txt`、`export.json` があります。3つすべての PCM24 stereo 48 kHz WAV は、フルスケールサンプル0でエンコードファイル検査に合格しました。この検査は、自然なリリース終端、両手演奏のしやすさ、主観的な音楽品質を証明しません。

[以前の評価](codex-live-transcription-evaluation.ja.md#artifact-recovery-and-reproduction)に記載した構成で、オプトインのアプリケーションテストを繰り返してください。自然なワークフローでは `natural_workflow:true` を設定し、正当な複数編集を1回のインポートとして扱わず、シーケンス全体の単一 Undo 観測を記録します。通常のリクエストでは `bundled_allowed:true` を設定します。名前付きセクションのテストは `ui::agent_chat::transcription_eval::installed_codex_composes_named_sections_in_the_window` です。設定から `audio` を省略します。実行にはログイン済みモデルとレビューの利用量を消費します。

検証: `cargo test --workspace` は、オプトイン／リソースによるスキップ20件を含む4,279テストに合格し、`cargo clippy --workspace --all-targets` とフォーマットも合格しました。最終レビュー固有の実行は8テスト、デスクトップ権限コントロールは13、共有 Python 測定テストは17に合格しました。3つの成功した実モデル試行は追加のオプトイン実行であり、最初のブロックされた試行は記録済みの失敗として残っています。
